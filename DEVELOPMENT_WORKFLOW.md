# Maintained project and release workflow

The authoritative project is `F:\Resolution File Manager project\ResolutionFileManager-Project-v6`. The Desktop project directory is a junction to it. The historical v6 name is not the current version. Read VERSION.txt and PROJECT_CONTEXT.md. Do not develop in a handoff, extracted ZIP, build output or temporary Work directory.

1. Complete development in this directory. Keep source, `locales`, `docs/help`, tests, icons, requirements and both platform builders together. Preserve older releases. Keep the complete English Help master in `docs/help/en.json`; edit its paragraphs explicitly, never replace it with translated summaries. Generate the readable master and locale Help from it. UI translations are separate and must not be retranslated as part of a Help update.
2. Run `python -m unittest discover -v` and `python tools/validate_help.py`. Run platform smoke tests using isolated settings. Record untested desktop integrations honestly.
3. Run `python tools/project_snapshot.py create "F:\Resolution File Manager project\Recovery Backups\VERSION-DATE-source" --zip`, with an unused destination. It copies tracked and untracked non-ignored source plus required Linux scripts, verifies every SHA-256 hash, and rejects mixed snapshots if source changes during copying. Review `python tools/project_snapshot.py candidates` before Git staging. Recover by extracting/copying a verified snapshot into a NEW directory; never overlay the sole current source.
4. Review the diff and create a local Git commit when authorised. Include all new locales, Help master, tooling and platform configurations. Do not commit caches, build environments, dist, generated release files or local settings. A source backup is recoverable without a commit; a commit alone does not contain untracked work. Never assume GitHub is current without checking its commit/version.
5. Build Windows using `build_windows.ps1` (fresh versioned Desktop EXE), and Linux using `sh build_linux.sh` on Linux. They consume the same source. Linux builds need Python/Tk, venv, FFmpeg/FFprobe/FFplay and a compatible graphics/audio environment. Use separate build and dist directories for each OS. Record OS/architecture/glibc baseline and test the resulting executable. A WSL Ubuntu test is not a Mint or laptop test.
6. Prepare releases under an unused versioned `release-output` directory. `build_windows_release.ps1` now refuses to erase an existing version. Create a Linux source handoff with the snapshot tool to a NEW versioned F: sibling directory; the zip contains a verified source manifest. Do not update old 12.3.0 handoffs in place. Verify the manifest after transfer and build from that source. Include exact binary hashes and test results with releases.
7. Publish GitHub commits, public releases or Store submissions only after approval. Store screenshots/listings/submission are a separate phase governed by the microsoft-store-submission skill.

`docs/RECOVERY_AUDIT_2026-10-19.md` explains the older duplicate folders, the original 12.3.0 help recovery and the backup locations. Root-level historic EXEs are rollback artifacts; run the current Windows binary from `dist/ResolutionFileManager.exe`, the Linux binary from `dist/linux`, or a clearly versioned Desktop/release file. Do not infer version from an unchanged folder name or file creation date.
